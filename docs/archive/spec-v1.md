# KMUTT Campus Chatbot — Project Spec

> เอกสารสรุปแนวคิดและสเปกสำหรับเริ่มพัฒนา
> ข้อมูลจริงของมหาวิทยาลัย (ราคา เวลาเปิดปิด รายละเอียดหลักสูตร ตำแหน่งตึก) ยังต้องเก็บเพิ่ม ทุกค่าที่ระบุว่า `TODO` หรือเป็นตัวอย่างในเอกสารนี้ห้ามนำไปใช้เป็นข้อมูลจริง

---

## 1. แนวคิดหลัก

chatbot ของ มจธ. ที่ไม่ใช่แค่ช่องแชท แต่เป็น **"แคมปัสที่คุยได้"**

- ผู้ใช้คุยกับ **ไกด์หลัก** ได้ทุกเรื่อง และคำตอบไปปรากฏบน **แผนที่แคมปัส** (ปักหมุด/ไฮไลต์สถานที่)
- กดตึกบนแผนที่เพื่อคุยกับ **ตัวละครประจำสถานที่** ที่เชี่ยวชาญเรื่องนั้นโดยเฉพาะ (รุ่นพี่แต่ละสาขา, ป้าโรงอาหาร, พี่บรรณารักษ์, พี่ฝ่ายรับสมัคร)
- ทุกตัวละครใช้ **ความจำร่วมกัน** และ **ส่งต่อกันได้** เมื่อคำถามอยู่นอกขอบเขตของตัวเอง

### กลุ่มผู้ใช้
1. นักเรียน ม.ปลายที่กำลังเลือกคณะ/สาขา (กลุ่มหลัก)
2. นักศึกษาปัจจุบัน (ที่อ่านหนังสือ ของกิน การเดินทางในแคมปัส)
3. ผู้ปกครอง

### จุดต่างจาก chatbot ทั่วไป
- คำตอบแสดงผลบนแผนที่ ไม่ใช่แค่ข้อความ
- ช่วย **ตัดสินใจ** เลือกสาขา ไม่ใช่แค่ให้ข้อมูล
- มีข้อมูลเชิงลึกจากการสัมภาษณ์รุ่นพี่จริง ซึ่ง LLM ทั่วไปไม่มี

## 2. โครงสร้างระบบ 3 ชั้น

```
┌────────────────────────────────────────────┐
│  แชทหลัก (ไกด์ "น้องบางมด")                  │  ← ประตูหน้า ถามได้ทุกเรื่อง
└───────────────┬────────────────────────────┘
                │ สั่งไฮไลต์ / ส่งต่อ
┌───────────────▼────────────────────────────┐
│  แผนที่แคมปัส                                 │  ← เชื่อมกับแชทสองทาง
└───────────────┬────────────────────────────┘
                │ กดตึก
┌───────────────▼────────────────────────────┐
│  ตัวละครประจำสถานที่ (persona)                │  ← ผู้เชี่ยวชาญเฉพาะเรื่อง
└────────────────────────────────────────────┘
        ทุกชั้นอ่าน/เขียน User Profile ก้อนเดียวกัน
```

### การเชื่อมแชท ↔ แผนที่
- **แชท → แผนที่:** LLM ตอบเป็นข้อความ + รายการ `place_id` ฝั่ง frontend นำไปไฮไลต์และปักหมุดเรียงลำดับ
- **แผนที่ → แชท:** กดตึก → สลับ persona ของแชทเป็นของสถานที่นั้น
- **การ์ดคำตอบ → แผนที่:** กดการ์ดสถานที่ในแชท แผนที่โฟกัสไปที่นั้น
- **ส่งต่อ (handoff):** persona แนะนำให้ไปคุยกับ persona อื่น พร้อมปุ่มพาไป

## 3. ฟีเจอร์

### MVP (ทำก่อน)
- [ ] แชทหลัก + แผนที่ที่เชื่อมกันสองทาง
- [ ] Persona 4 จุด: 2 คณะ/สาขา, โรงอาหาร, ฝ่ายรับสมัคร
- [ ] ปักหมุดสถานที่จากคำตอบ (เฉพาะ `place_id` ที่มีในฐานข้อมูล)
- [ ] ความจำร่วมระหว่าง persona (User Profile)
- [ ] Handoff ระหว่าง persona
- [ ] อ้างอิงแหล่งที่มาและวันที่อัปเดตในคำตอบ
- [ ] Quick reply chips (ผู้ใช้ไม่ต้องพิมพ์เองทุกครั้ง)

### เฟส 2
- [ ] Major Matchmaker: ถามคำถามเชิงความชอบ → คะแนนความเข้ากันของแต่ละสาขา → ตึกคณะเรืองแสงตามคะแนน
- [ ] สะสมแสตมป์เมื่อแวะสถานที่ → สรุปสาขาที่เหมาะ
- [ ] โหมดเปรียบเทียบสาขาที่คนสับสน
- [ ] Mini challenge: ลองโจทย์ 5 นาทีของแต่ละสาขา
- [ ] คำตอบที่ขึ้นกับเวลา (กรองสถานที่ที่เปิดอยู่ตอนนี้)
- [ ] ปุ่ม "ตอบไม่ตรง"

### เฟส 3 / แผนอนาคต
- [ ] แดชบอร์ดฝั่งมหาลัย: คำถามยอดนิยม, สาขาที่คนสนใจ, คำถามที่ตอบไม่ได้, ให้เจ้าหน้าที่คณะอัปเดตข้อมูลเอง
- [ ] เลเยอร์กิจกรรมบนแผนที่ (Open House, วันสัมภาษณ์)
- [ ] เส้นทางเดิน (รวมเส้นทางรถเข็น / มีหลังคา)
- [ ] ภาษาอังกฤษ
- [ ] ช่องทาง LINE OA

## 4. Data Models

### 4.1 Place
```json
{
  "id": "food_court_1",
  "name_th": "โรงอาหาร",
  "name_en": "Food Court",
  "type": "food | faculty | study | service | facility",
  "persona_id": "aunt_food",
  "map": { "x": 0.06, "y": 0.60, "w": 0.36, "h": 0.32 },
  "tags": ["ราคาประหยัด", "นั่งกลุ่มได้"],
  "hours": [{ "days": "mon-fri", "open": "TODO", "close": "TODO" }],
  "description": "TODO",
  "updated_at": "YYYY-MM-DD",
  "source": "TODO"
}
```
- `map` ใช้พิกัดแบบสัดส่วน (0–1) บนภาพแผนที่ที่วาดเอง เพื่อให้ responsive
- `tags` ใช้กรองคำถามแนว "ที่ไหนเงียบ / มีปลั๊ก / เปิดดึก"

### 4.2 Persona
```json
{
  "id": "senior_fibo",
  "display_name": "พี่ภูมิ ปี 3",
  "role": "รุ่นพี่สาขาหุ่นยนต์",
  "place_id": "fibo",
  "scope": ["หลักสูตร", "ชีวิตการเรียน", "โปรเจกต์", "ฝึกงาน"],
  "out_of_scope_handoff": { "อาหาร": "aunt_food", "สมัครเรียน": "admission" },
  "tone": "เป็นกันเอง พูดตรง ใช้ภาษาวัยรุ่นพอประมาณ",
  "greeting": "TODO",
  "starter_chips": ["วิชาไหนโหดสุด", "ต่างจากวิศวะเครื่องกลยังไง"],
  "knowledge_namespace": "fibo"
}
```

### 4.3 User Profile (ความจำร่วม)
```json
{
  "session_id": "uuid",
  "role_guess": "highschool | student | parent | unknown",
  "interests": ["หุ่นยนต์", "เขียนโค้ด"],
  "visited_places": ["food_court_1", "fibo"],
  "major_scores": { "comp_eng": 0.32, "robotics": 0.41 },
  "notes": ["ชอบลงมือสร้างของจริง"]
}
```
- เก็บเท่าที่จำเป็น ไม่ผูกกับตัวตนจริง (ไม่เก็บชื่อ เบอร์ อีเมล)

## 5. LLM Response Contract

ทุกคำตอบจาก LLM ต้องเป็น JSON ตามนี้ (ใช้ structured output / tool calling)

```json
{
  "message": "ข้อความที่แสดงในแชท",
  "places": [
    { "place_id": "library", "reason": "เงียบ มีปลั๊ก เหมาะอ่านคนเดียว" }
  ],
  "handoff": { "persona_id": "librarian", "label": "คุยกับพี่บรรณารักษ์ต่อ" },
  "chips": ["เปิดกี่โมง", "จองห้องติวยังไง"],
  "profile_update": { "interests_add": ["อ่านหนังสือ"] },
  "sources": [{ "title": "TODO", "url": "TODO", "updated_at": "YYYY-MM-DD" }]
}
```

กฎ:
- `place_id` ต้องอยู่ในฐานข้อมูลเท่านั้น backend ต้อง validate และตัดค่าที่ไม่มีทิ้ง
- `handoff`, `chips`, `profile_update` ใส่หรือไม่ใส่ก็ได้
- ถ้าไม่มีข้อมูลรองรับ ให้ตอบว่าไม่รู้และแนะนำช่องทางติดต่อ ห้ามเดา

## 6. Prompt Design

### โครง system prompt (ประกอบตอน runtime)
1. **Base rules** (ทุก persona): ตอบจากข้อมูลที่ให้เท่านั้น, อ้างอิงแหล่ง, ไม่รู้ให้บอกว่าไม่รู้, ตอบเป็น JSON ตาม contract
2. **Persona block**: ชื่อ บทบาท โทน ขอบเขต กฎ handoff
3. **User profile**: สรุปสิ่งที่รู้เกี่ยวกับผู้ใช้
4. **Retrieved context**: เอกสารจาก RAG (namespace ของ persona + namespace กลาง)
5. **Place list**: รายการ `place_id` + tags + เวลาเปิด (ย่อ) เพื่อให้เลือกปักหมุดได้
6. **Current time**: สำหรับคำตอบที่ขึ้นกับเวลา

### ไกด์หลัก
- ตอบเรื่องทั่วไปได้ทุกเรื่อง ปักหมุดเสมอเมื่อคำถามเกี่ยวกับสถานที่
- เมื่อคำถามลึกเฉพาะทาง ให้ตอบสั้นแล้ว handoff

## 7. RAG / Knowledge Base

| Namespace | เนื้อหา | แหล่ง |
|---|---|---|
| `general` | ข้อมูลทั่วไป มจธ., การเดินทาง, วิทยาเขต | เว็บมหาลัย |
| `<major_id>` | หลักสูตร, รายวิชา, อาชีพ, บทสัมภาษณ์รุ่นพี่ | เอกสารหลักสูตร + สัมภาษณ์ |
| `food` | ร้าน, เมนู, ช่วงราคา | เก็บเอง / นักศึกษาช่วยอัปเดต |
| `admission` | รอบ TCAS, เกณฑ์, เอกสาร | ประกาศรับสมัคร |

- ทุก chunk มี metadata: `source`, `updated_at`, `namespace`
- บทสัมภาษณ์รุ่นพี่ต้องได้รับอนุญาตก่อนใช้

## 8. UI / UX

### Desktop
- ซ้าย: แผนที่แคมปัส (ภาพวาดเอง, ไม่ต้องเป๊ะตามจริง แต่สื่อตำแหน่งได้)
- ขวา: แชท (header แสดง avatar + ชื่อ persona ปัจจุบัน)

### Mobile
- แผนที่ครึ่งบน, แชทเป็น bottom sheet ลากขึ้นลงได้ (แบบแอปแผนที่)

### องค์ประกอบสำคัญ
- หมุดมีเลขลำดับตรงกับการ์ดในแชท
- สถานที่ที่ไม่เกี่ยวข้องจางลงเมื่อมีการไฮไลต์
- แสดง "ความจำ" ใต้ header เช่น "จำได้ว่าน้องเคยแวะ FIBO"
- Quick reply chips + ช่องพิมพ์อิสระ
- ปุ่ม handoff แบบ "→ คุยกับ...ต่อ"
- แสดงวันที่อัปเดตข้อมูลในคำตอบ

## 10. ความเสี่ยงและแนวทางรับมือ

| ความเสี่ยง | แนวทาง |
|---|---|
| ข้อมูลเปลี่ยนบ่อย (ราคา, เวลา) | แสดง `updated_at`, แดชบอร์ดให้คณะ/ผู้ดูแลแก้เอง |
| บอทตอบผิด / มั่ว | จำกัดขอบเขต persona, อ้างอิงแหล่ง, validate `place_id`, ให้ตอบว่าไม่รู้ได้ |
| ความเป็นส่วนตัว | เก็บโปรไฟล์ขั้นต่ำ ไม่ผูกตัวตน |
| Scope บาน | ยึด MVP 4 จุดก่อน |

## 11. การวัดผล

- ชุดคำถามทดสอบ (เช่น 50–100 ข้อ) พร้อมคำตอบที่ถูก → วัดความถูกต้อง
- ทดสอบกับนักเรียน ม.ปลายจริง: เทียบเวลาและความพึงพอใจกับการหาข้อมูลจากเว็บมหาลัยเอง
- เก็บ log คำถามที่ตอบไม่ได้ เพื่อเติมข้อมูล
